Packages

Strut uses familiar angle-bracket syntax for both standard-library modules and package modules. Quoted includes are reserved for local project/native headers. Angle brackets are semantic Strut module loads, not a promise to inject a same-named C++ header.

Standard and package includes

include <filesystem>; // Strut standard module
include <example>;    // dependency declared by this project's strut.json

HTTP and SQLite are currently dependency-driven runtime APIs and need no include; their documentation lists the native development libraries required at link time. An angle-bracket name that is not a standard module is resolved as a project dependency.

Local include

include "auth.h";
include "models/user.h";

Package direction

Official packages are intended to live under a dedicated Strut packages organisation. HTTP, SQLite, PostgreSQL, TLS, and WebSocket support are examples of functionality that can evolve independently from the language runtime.

Core facilities that directly define the language experience—such as strings, collections, JSON, basic IO, process execution, and concurrency primitives—remain available without turning every small program into a dependency-management exercise.

Project manifest

Strut projects and packages use a JSON strut.json manifest. JSONIC is used by the bootstrap compiler to parse and validate the format.

{
  "name": "todo-service",
  "version": "0.1.0",
  "entry": "src/main.p",
  "dependencies": {
    "http": "^0.2.0",
    "sqlite": "~0.3.1"
  }
}

Version requirements

Initial requirements deliberately stay small: exact 1.2.3, compatible ^1.2.3, patch-compatible ~1.2.3, and *. Floating labels such as latest are not part of the reproducible package contract.

Lockfile

strut.lock.json records exact versions, immutable source revisions, content checksums, and transitive dependency edges. Normal builds consume the lock without silently upgrading dependencies.

Shared cache

Packages are cached once per user rather than copied into every project. STRUT_HOME can override the base location; otherwise Strut follows the platform cache convention on Linux, macOS, and Windows.

Run strut project to see the exact project root and cache path currently in use. If a declared dependency is unavailable, strut install reports the missing package and requirement; local packages enter the cache through strut add <path>. Remote registry acquisition is not yet supported.

Package CLI

The current package CLI supports deterministic local/cache workflows. Strut now has an HTTP client, but remote package fetching is intentionally still separate from the package resolver until its registry/security contract is designed.

strut add ../http
strut list
strut install
strut remove http

include <name> resolves the package entry declared by the cached version selected from the project manifest. include <name/path.h> resolves an explicit package file.

Authoring a package

An official-style package has a strut.json manifest, a declared entry header, source/header files, tests, and documentation. Package paths are validated so metadata cannot escape the package root.

{
  "name": "example",
  "version": "0.1.0",
  "include": "include/example.h"
}

Dogfood workflow

The repository includes clean-environment package dogfood fixtures. They initialise a fresh project, add local packages, install them into an isolated shared cache, resolve include <package>, compile the application, and execute it.
